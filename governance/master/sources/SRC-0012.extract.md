## Decision 1 — Universal, Seeded and Configurable Monetary Policy

### Owner decision

All monetary policies, rules, calculation methods and supported options that already exist in LUXORA must be seeded into the governed configuration system. At initial setup, an authorized administrator must be able to discover, inspect, select, configure, validate, simulate, approve and activate any applicable seeded rule without modifying application code.

This requirement applies to, but is not limited to:

1. **Currencies and monetary precision:** supported currencies, minor-unit precision, permitted scales, currency-specific constraints and rounding policies.
2. **Rounding:** supported rounding modes, intermediate versus final rounding, rounding boundaries, precision constraints and treatment of residual differences.
3. **Pricing:** base prices, price components, price adjustments, price overrides, price lists, price validity periods and applicable pricing policies.
4. **Taxation:** configurable tax rules, rates, inclusive or exclusive tax treatment, calculation bases, line-level and order-level calculations, exemptions and jurisdiction-specific policy parameters.
5. **Discounts and promotions:** discount types, fixed and percentage discounts, stacking, precedence, caps, eligibility, allocation, expiration and reversal rules.
6. **Fees and commissions:** platform fees, seller commissions, transaction charges, service fees, provider fees, fee allocation and applicable minimums, maximums or tiers.
7. **Refunds and reversals:** full and partial refunds, eligibility, limits, proportional allocation, tax reversals, discount reversals, voucher and wallet effects, idempotency and reconciliation policies.
8. **Settlements and payouts:** settlement schedules, seller balances, fees, deductions, reserves, payout eligibility, rounding adjustments, reconciliation and exception handling.
9. **Currency conversion:** supported currency pairs, conversion methods, rate sources, rate timestamps, rate validity, spreads, conversion fees and rounding policies.
10. **Financial reconciliation:** matching rules, tolerances, discrepancy classification, exception workflows, unresolved transaction handling and audit requirements.
11. **Financial exceptions:** ambiguous legacy records, invalid precision, overflow, missing currencies, conflicting policies, residual amounts and operator-resolution workflows.
12. **Future monetary capabilities:** newly introduced rules, calculation methods, currencies, payment methods, financial products and other monetary policies must be registerable and configurable without unnecessary changes to the shared platform core.

### Mandatory seeding requirements

**A. Seed every existing supported rule**

Before release, inventory the existing source code, configuration files, database defaults, provider integrations, tests and documented monetary behavior. Identify every supported monetary rule and option currently implemented.

Convert that inventory into canonical, structured configuration records. The inventory must cover actual existing behavior, not merely examples or a proposed list of future features.

Every discovered rule must be classified as one of:

- Seeded and configurable.
- Seeded but awaiting approval or activation.
- Intentionally fixed by a documented financial or security invariant.
- Unsupported or requiring implementation before it can be offered as a configuration option.
- Deprecated, with its replacement and migration path recorded.

A rule must not be marked configurable merely because a placeholder record exists. The implementation must actually consume and enforce the selected configuration.

**B. Make seeded rules available during initial configuration**

Seeded rules must be visible through the appropriate authorized administration interface and configuration API. Each rule must have a stable identifier, description, schema, supported options, defaults, validation requirements, scope, dependencies, precedence, effective dates, version and lifecycle status as applicable.

Administrators must be able to inspect available options before activating a rule. Unsupported combinations must be rejected with an actionable explanation.

**C. Seed definitions and defaults separately from live configuration**

Maintain a canonical source for rule definitions and versioned seed templates. Store tenant-, business-, jurisdiction-, currency- and provider-specific settings at their appropriate configuration scope.

A default is a starting configuration, not an invisible code fallback. Any operational default must be explicit, documented and inspectable. Sensitive financial settings must not become active merely because a seed file exists; activation and approval requirements must be enforced.

**D. Make seeding deterministic and safe to repeat**

The seed process must be idempotent, versioned, auditable and safe to rerun.

- Repeated execution must not create duplicate rule definitions or configurations.
- Existing operator-approved configurations must not be silently overwritten.
- Seed updates must be explicit, diffable and governed by a documented merge or migration policy.
- Removed or deprecated seed definitions must not silently delete historical financial evidence or active configuration.
- Failed seeding or migration must be handled safely, with transaction boundaries and recovery behavior appropriate to the data store.
- The platform must report missing, invalid, conflicting, outdated and unapplied seed definitions.

**E. Make future rules extensible**

New rules must be registerable through a governed definition and schema mechanism. Where a new rule can be expressed by an existing supported rule engine, administrators should be able to configure it without a code deployment.

When a new rule requires previously unsupported computational behavior, protocol support or an extension to the rule engine, implementation may be necessary. The new capability must then be registered, validated, tested, documented and made available through the same configuration mechanism. Do not claim a new capability exists until its executable behavior is implemented.

**F. Preserve financial invariants**

Configurability must never permit silent rounding, invalid monetary scales, mixed-currency arithmetic without an explicit conversion, overflow, unauthorized changes to posted transactions or bypassing of required accounting controls.

Financial policies must be versioned and traceable to the transactions that used them. Replaying or auditing a historical calculation must use the applicable historical policy version and the necessary recorded inputs, rather than silently applying today's configuration.

### Required implementation and acceptance evidence

Engineering must:

1. Inventory existing monetary rules and options from the actual repository and map each to its canonical configuration record.
2. Identify all hardcoded business assumptions and classify whether each should become configuration, remains a fixed invariant, or requires new implementation.
3. Implement and test the seed registry, seed migrations, administrative discovery, schemas, validation, activation and audit history.
4. Prove that every supported existing rule can be discovered and configured at the appropriate scope.
5. Prove that repeated seeding creates no duplicates and does not overwrite approved live configurations.
6. Test invalid options, conflicting rules, precedence, effective dates, rollback, tenant isolation and financial invariants.
7. Demonstrate that adding a rule supported by the existing engine requires configuration rather than a core-code change, and document cases requiring new executable implementation.
8. Publish a traceability matrix linking every inventoried rule to its seed definition, implementation, configuration interface, tests and evidence.
9. Keep production readiness blocked for any in-scope monetary rule that is missing, incorrectly seeded, not actually configurable as claimed or insufficiently tested.

**Acceptance principle:** All currently implemented and supported monetary rules are seeded, discoverable and configurable within their intended scope, subject to authorized approval and invariant-preserving constraints. Future supported rules can be added through the same governed extension mechanism. No hardcoded business default may silently override the effective approved configuration.
