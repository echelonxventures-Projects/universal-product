🏛️ Platform Owner / Super Administrator Guide

URL: http://localhost:8787/platform.html · sign in with the platform account (platform@luxora.shop in the seed). Platform identity is separate from any store — a platform admin sees every store, a store admin sees exactly one.

One principle: everything — every screen, dataset, provider, theme, role, capability and offer — is declared data, not code. The console is organized the way the architecture declares: twelve sections, one canonical home per capability, and every navigation leaf resolves to a live view. Nothing is a placeholder, nothing is orphaned.

How any leaf resolves

A leaf is never a dead link — it renders in exactly one of three ways:

  • A dedicated view (Tenants, Billing Ops, Ops Hub…) — purpose-built screens.
  • An entity dataset — a cross-store table over a declared entity, built from the same field definitions the Store Console renders.
  • A universe dataset — a corpus-declared domain: its registry record plus its live records.

The dataset toolbar (used everywhere a dataset renders)

  • Filter box — per-table; matches any visible column or the record id.
  • + New / Edit / ✕ — records are created/changed through the platform write endpoints, on a form built from the entity's own declaration. Datasets your role may not write hide the buttons — and the endpoints refuse the same writes.
  • ⇪ Import — paste JSON or CSV (header row = column names); download a sample file in this dataset's own columns; each rejection comes back with its row number and reason. Store-scoped datasets require you to name the store.
  • ⇩ Export — every format the server can emit, scoped platform-wide or to one store.

Cross-store oversight (Global Operations)

The Store Console edits one store; the Global Operations views watch all of them. Two primitives back every view: a cross-store dataset table (the same records each store edits, read platform-wide) and a fan-out that runs each store's own read-only handler once per store and merges — so business logic lives exactly once. Each view lives in its canonical section: Orders · Fulfilment (04 Commerce), Catalog · SKUs (02 Knowledge), Sellers · B2B · Trade (03 Business), Ads · Marketplace (04), Finance · Payments (04), Offers · Affiliates (04), Support · SLA (05 Operations), Content · UGC (06), Risk · Compliance · Trash (08), Team · Access · Settings (11), Analytics · A/B (07), Data Explorer (10). The 🧭 Ops Hub (05 Operations) is the fleet overview.

Role gating

If your platform role does not grant a section, that leaf is hidden and the view refuses to render even if you reach it by URL — the back-end refuses the same call. See Roles above.

📦 Store Administrator Guide

URL: http://localhost:8787/admin.html · sign in with the store's admin account. You must be pointed at the right store — use ?store=<slug> or the <slug>.localhost subdomain. An admin of one store has no access to another store's data.

One console, two scopes. The store console and the platform console are also reachable as one app at /console.html: a single sign-in, one nav grouped by scope (your store sections, then any platform sections your role grants), and a ⇄ switch in the top bar to flip between scopes with no second login. If you hold both a store and a platform role, start there.

Good practice

  • Keep a written reason on every return, RFQ and refund — the audit trail carries it.
  • Prefer the guided flows over raw Data Studio edits when money or tax is involved.
  • If a change touches payments, taxes or store configuration and you're unsure, escalate to a senior admin or the platform team (Part E of the manual covers what they can do).
